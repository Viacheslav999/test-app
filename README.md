Веб-приложение “социальный вишлист”: владелец создаёт списки желаний, добавляет товары (название/ссылка/цена/картинка) и делится публичной ссылкой. Друзья могут **резервировать подарки** (чтобы не повторяться) и **скидываться** на дорогие вещи. Обновления статусов и прогресса происходят **в реальном времени** без перезагрузки (Socket.IO).

## Основные фичи

### Для владельца
- Регистрация/вход (email + пароль).
- Создание нескольких вишлистов (ДР, Новый год и т.д.).
- Получение публичной ссылки на каждый вишлист.
- Управление товарами в списке (добавление/скрытие/архивация — зависит от UI).

### Для гостей по публичной ссылке (без регистрации)
- Просмотр списка.
- **Резервирование** подарка.
- **Сбор средств** на подарок (если включено `allow_funding` и есть `price`).
- Статус брони и прогресс сбора обновляются **в реальном времени**.

## Как проверить (готовые сценарии)

### Сценарий A — публичная страница без логина
1. Открой публичный вишлист: `/w/<public_slug>` (без регистрации).
2. Нажми **“Зарезервировать”** у товара.
3. Открой ту же страницу во **второй вкладке**/в другом браузере:
   - статус станет **“Зарезервировано”** без перезагрузки.
4. Нажми **“Снять бронь (если это ты)”** — бронь снимается только тем же гостем.

### Сценарий B — сбор средств и прогресс-бар
1. На публичной странице у товара с включенным `allow_funding` введи сумму и нажми **“Внести”**.
2. Во второй вкладке прогресс и “Собрано €X из €Y” обновятся **мгновенно**.
3. Проверь edge-кейс: внеси сумму больше цели — сервер **не даст переполнить** (см. ниже).

### Сценарий C — владелец + публичный просмотр
1. Зарегистрируйся и создай вишлист.
2. Скопируй публичную ссылку, открой в приватном окне.
3. Резервируй/вноси вклад как гость и наблюдай обновления в реальном времени.

## Продуктовые решения

- **Публичная ссылка без регистрации** — гость может сразу бронировать/скидываться.
- **Секретность сюрприза**:
  - владелец видит статус (зарезервировано/нет) и общий прогресс по сбору,
  - **не видит кто** зарезервировал,
  - **не видит кто сколько** внёс (нет персональных данных по вкладам).
- **Анти-переполнение сбора**: сервер обрабатывает вклад так, чтобы общий сбор **не превысил цену** товара (клампит вклад “по остатку”).
- **Realtime “обязателен”**: обновления уходят всем наблюдателям через Socket.IO события без перезагрузки.
- **UX fallback**: текущая вкладка после действий также делает `load()` (refetch), чтобы UI был консистентный даже при проблемах сети.

## Edge cases (как решено)

### Конкурентная бронь
- Если два человека одновременно бронируют один товар:
  - первый успешно,
  - второй получает `409 Already reserved`.
- Все клиенты получают realtime-событие `reservation_changed`.

### Конкурентные взносы / переполнение цели
- Вклад обрабатывается на сервере с блокировкой строки (transaction + `FOR UPDATE` на item).
- Если до цели осталось 3€, а пользователь пытается внести 10€:
  - сервер запишет вклад **3€**,
  - вернёт обновлённый `funded_amount`,
  - всем клиентам отправится realtime-событие `funding_progress`.

### Товар без цены / сбор выключен
- Если `price == null` → сбор недоступен.
- Если `allow_funding == false` → эндпоинт вклада вернёт `400 Funding disabled`.

### Архивация/удаление товара
- `archived == true` → публичные действия (reserve/contribute) для такого товара запрещены (404/400).

## Архитектура и realtime

### Стек
- Frontend: **Next.js (App Router)**, React
- Backend: **FastAPI**
- DB: **PostgreSQL**
- Realtime: **Socket.IO** (ASGI app поверх FastAPI)
- Deploy: **Railway**

### Realtime: как это работает
1. Клиент подключается к Socket.IO серверу (backend):
   - `io(SOCKET_URL, { transports: ["polling","websocket"] })`
2. Клиент “заходит” в комнату вишлиста:
   - `socket.emit("join_wishlist", { wishlist_id })`
3. Backend после действий (reserve/unreserve/contribute) делает:
   - `sio.emit(..., room="wishlist:<id>" )`
4. Клиенты слушают события и обновляют UI.

### События
- `reservation_changed`  
  Payload: `{ item_id: number, reserved: boolean }`
- `funding_progress`  
  Payload: `{ item_id: number, funded_amount: number, target_amount?: number }`

## API (коротко)

### Публичные действия (без регистрации)
- `POST /public/reserve`  
  body: `{ slug, item_id, guest_token? }`
- `POST /public/unreserve`  
  body: `{ slug, item_id, guest_token }`
- `POST /public/contribute`  
  body: `{ slug, item_id, amount, currency, guest_token? }`

### Владелец (нужен JWT)
- `GET /wishlists` — список вишлистов пользователя
- `POST /wishlists` — создать вишлист
- `GET /wishlists/public/{slug}` — публичный просмотр

## QA / быстрые проверки в браузере

### Проверка, что Socket.IO реально работает
1. Открой DevTools → Network → фильтр `socket.io`.
2. Должен быть запрос:
   - `.../socket.io/?EIO=4&transport=websocket` со статусом **101** (Switching Protocols)
3. Открой вторую вкладку:
   - действие в первой вкладке должно обновиться во второй без F5.

Product decisions & edge cases

Удаление товара с вкладом. Товары не удаляются физически — используется флаг archived.
Если на товар уже вносили средства, он остаётся видимым в истории, но новые резервы и вклады запрещены. Это предотвращает потерю контекста и денег.

Переполнение суммы. Сервер обрабатывает вклад в транзакции и ограничивает сумму по остатку до целевой цены. Клиент никогда не может “перелить” больше цели.

Конкурентные действия.
— двойная бронь предотвращается сервером (409).
— конкурентные вклады синхронизируются транзакцией + realtime событиями.

Секретность сюрприза. Владелец видит только статус и общий прогресс, но не видит кто бронировал и кто сколько внёс.

Realtime как default. Все публичные страницы автоматически подключаются к Socket.IO и получают обновления без перезагрузки; для надёжности текущая вкладка дополнительно делает refetch после действия.

Гость без регистрации. Для гостей используется guest_token в localStorage, чтобы ограничить снятие брони только тем, кто её поставил.
